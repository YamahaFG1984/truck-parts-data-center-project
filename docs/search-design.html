智能搜索详细设计

这是整个系统的心脏：客户给一个编号、一句话或一张照片，系统要在几秒内落到唯一的 SKU 上。本文讲清四件事——为什么这样设计、业务上怎么串起来、数据怎么流动、关键代码在做什么。

1. 为什么它是核心

总经理的原话是"从图片到功能再到价格"。拆开看，价格和功能都在库里现成躺着，难的是把客户嘴里那个东西对上我们的 SKU。对上了，图片、规格、适配、三家成本、建议售价、替代件全都是一次查询就能拿到的附属品；对不上，后面所有功能都无从谈起。

所以这个功能的目标不是"搜得到"，而是把销售的响应时间从几小时压到几秒，并且答案可解释——每条结果都要说清"我为什么认为是它"。

2. 客户的输入有多脏

设计从真实输入开始。同一个 Volvo 制动气室编号 26570367，在询盘里见过这些写法：

客户实际输入为什么会这样归一化后
26570367正常26570367
2657-0367手工敲号习惯加分隔26570367
2657 0367从 PDF 目录复制，空格是排版留下的26570367
２６５７０３６７中文输入法下的全角数字26570367
26570367 Volvo顺手把品牌也写上编号 + 品牌线索
7426570367雷诺的同件号：74 + Volvo 号互换号，指向同一个件
265703?7照片上的铭牌磨掉一位只能模糊匹配
brake chamber volvo fh12客户压根没有编号走文本检索

结论很直接：任何比对之前都必须先归一化，而且写入和查询必须用同一份实现，否则库里存的和查询算出来的对不上。这就是 normalize_number() 在全系统只有一份、被模型 save()、导入服务和搜索同时调用的原因。

3. 设计原则与取舍

决定备选方案为什么这样选放弃了什么
匹配只查自家数据库，大模型不参与判断让 LLM 直接回答"这个 OE 号是什么件"大模型没有我们的库，问它编号一定会编。编号匹配是确定性检索，命中就是 100% 准确；AI 只在读图和写文案的位置出现。"看起来更智能"的演示效果
三级降级：精确 → 前缀 → 模糊一上来就全表模糊90% 的询价是能精确命中的，先跑最便宜的查询，命中唯一结果立即返回；模糊只在前面都没结果时兜底。既快又不会让高质量结果被相似项淹没。实现上多几个分支
pg_trgm 做模糊Elasticsearch、向量检索编号是短字符串，字符级 trigram 恰好适用；PostgreSQL 一个 GIN 索引解决，不引入第二套存储和同步问题。语义检索能力（列入演进路线）
每条结果带 match_type 与 score只返回一个"最佳答案"销售需要知道该不该再核对一遍。"精确"可以直接报价，"模糊 0.62"必须看图确认。可解释比准确率数字更有用。界面上多一个标签
exact 与 normalized 分开都算精确能对客户说"您给的格式带横杠，我们认出来了"，也提醒运营这个编号在库里的写法与客户习惯不同。—
一个产品只保留最佳候选每个命中的编号一条结果一个产品可能挂 5 个 OE 号，同时被精确和模糊命中；列表里出现 5 次同一个 SKU 是噪音。—
SQLite 回退只支持 PostgreSQL没有 docker 的机器也能演示，`pg_trgm` 不可用时退化为 difflib。测试在两个库上都跑，避免"只在一个库上正确"的代码。回退路径的模糊质量较差，且需要多写一段

4. 业务链路

一次询价从输入到留痕的完整链路。注意三个"人工确认"的位置——系统从不替人拍板。

时序上，页面是边打字边查的：输入停止 300 毫秒后 HTMX 发一次请求，只替换结果区；每次查询在返回前写一条询价记录（一个 INSERT，不额外读库）。

5. 第一步：归一化

四步纯函数，没有任何模型依赖，因此可以被入库路径和查询路径共用：

def normalize_number(raw: str | None) -> str:
    """Full-width to half-width, drop every non-alphanumeric character, upper-case."""
    if raw is None:
        return ""
    text = unicodedata.normalize("NFKC", str(raw))
    return _NON_ALNUM.sub("", text).upper()

几个刻意的决定：

  • NFKC 而不是手写全角表：一行搞定全角数字、全角字母、部分兼容字符，还顺手处理了从 Excel 复制来的不可见字符。
  • 保留前导 0：Bosch 的 0 986 467 422 归一化后是 0986467422，前导 0 是编号的一部分。这也是导入时所有单元格按文本读取的原因——一旦被 Excel 当数字，前导 0 就没了。
  • 非拉丁文本归一化后为空：纯中文输入不会被误当成编号，自然落到文本检索分支。
  • 一格多号要先拆再归一：split_numbers() 固定按 , ; 、 | 和换行拆；斜杠只在两侧都够长时才拆——20443906/20568713 是两个号，而 MANN 滤芯 WK 1080/7 是一个号。这条规则是从真实供应商表里抠出来的。

6. 第二步：输入分流

归一化之后要先判断"这是什么"，再决定走哪条检索路径。判定按固定顺序短路：

def detect_query_kind(raw, sku_prefix=None) -> Literal["sku", "number", "text"]:
    explicit, text = split_query_prefix(raw)      # sku: / oe: / name: 显式前缀优先
    if explicit:
        return explicit
    norm = normalize_number(text)
    if not norm or not any(ch.isdigit() for ch in norm):
        return "text"                             # 没有数字，不可能是编号
    if prefix_norm and norm.startswith(prefix_norm):
        return "sku"                              # 以 FIT- 开头
    letters = sum(ch.isalpha() for ch in norm)
    if len(norm) >= 5 and letters / len(norm) < 0.5:
        return "number"                           # 够长、数字为主
    return "text"
三个前缀的真实语义。sku: 和 name: 会切换到对应的检索分支；oe: 的意思是"把它当编号查"，让 brake 123 这种会被判成文本的输入强制走编号匹配，它并不限定只搜 kind=OE 的编号——编号匹配一视同仁地查 OE、互换号和供应商料号，因为客户并不知道自己手里的号属于哪一类。

7. 第三步：三级匹配

三级的顺序、短路与降级条件：

def search(raw, *, limit=MAX_RESULTS) -> list[Candidate]:
    _, text = split_query_prefix(raw)
    kind = detect_query_kind(raw)
    norm = normalize_number(text)
    if not norm and not text.strip():
        return []

    if kind == "sku":
        return _by_sku(text, limit)
    if kind == "text":
        return _by_name(text, limit)

    found = _exact(_as_typed(raw), norm)
    if len({c.part.pk for c in found}) == 1:
        return _best_per_part(found)          # 唯一命中：不再往下跑
    if len(found) < limit:
        found += _prefix(norm, limit)
    if len(_best_per_part(found)) < limit:
        found += _fuzzy(norm, limit)
    return _best_per_part(found)[:limit]

两处短路值得注意：L1 命中唯一一个产品就直接返回（最常见的情形，代价是一条索引查询）；命中多个产品时反而要继续——那说明这个号挂在几个 SKU 上，销售需要看到更多线索来挑，此时补上前缀与模糊结果反而有用。

7.1 L1 精确与归一化

def _exact(typed: str, norm: str) -> list[Candidate]:
    rows = PartNumber.objects.filter(number_norm=norm).select_related("part__category__parent")
    return [
        _candidate(pn, "exact", 1.0) if pn.number == typed else _candidate(pn, "normalized", 0.95)
        for pn in rows
    ]

查询只用 number_norm 的索引，一条 SQL。exact 与 normalized 的区别不在数据库层，而在与"原样输入"的字符串比较：_as_typed() 剥掉 oe: 之类的前缀，但不做全角折叠。所以客户输入全角 ２６５７０３６７ 时命中的是 normalized——界面会说"归一化后命中"，这正是我们想告诉销售的事实。这个细节曾经写反过：早期版本拿归一化后的串去比，全角输入被标成"精确"，但显示的编号和客户输入的明显不同，反而让人困惑。

7.2 L2 前缀 / 包含

处理带后缀的变体（20443906-1）、带前缀的写法（VOLVO20443906）、以及客户把两个号连在一起发过来的情况。双向包含：

cond = Q(query__contains=F("number_norm")) & Q(norm_len__gte=MIN_CONTAINED_LEN)
if len(norm) >= MIN_CONTAINED_LEN:
    cond |= Q(number_norm__contains=norm)
...
_candidate(pn, "prefix", 0.8 * min(len(norm), pn.norm_len) / max(len(norm), pn.norm_len))

MIN_CONTAINED_LEN = 5 是这一级的安全阀：库里短于 5 位的编号不参与"被包含"判断，否则一个 123 的编号会命中几乎所有查询。打分用长度比而不是常数，是为了让"多一位后缀"排在"多五位"前面。

7.3 L3 模糊

只在前两级都不足时才跑，且归一化后少于 3 个字符直接放弃（太短的串和什么都相似）。两个数据库走两条路：

rows = (
    PartNumber.objects.filter(number_norm__trigram_similar=norm)   # 命中 GIN 索引
    .annotate(similarity=TrigramSimilarity("number_norm", norm))
    .filter(similarity__gte=FUZZY_THRESHOLD)                       # 0.45
    .exclude(number_norm=norm)
    .order_by("-similarity")[: limit * 3]
)

先用 trigram_similar 让 GIN 索引筛掉绝大多数行，再算精确相似度排序——反过来写会变成全表算分。阈值 0.45 是量出来的：7–8 位编号错一位大约落在 0.45–0.55，错两位掉到 0.3 以下。SQLite 回退用 difflib，阈值必须提到 0.75（两种算法的分布不同），并且先用首三位或末三位从库里取不超过 2000 行做候选池，避免在 Python 里扫全表。

8. 文本与 SKU 分支

没有编号的查询走两段式：先字面 AND 过滤，全不中再用 trigram 兜错拼写。

for token in tokens:
    brand = canonical_brand(token)                 # "沃尔沃" / "benz" / "howo" → 标准品牌名
    cond = (
        Q(name_en__icontains=token) | Q(name_zh__icontains=token)
        | Q(category__name__icontains=token) | Q(category__name_en__icontains=token)
        | Q(fitments__model__icontains=token) | Q(fitments__make__icontains=brand or token)
    )
    qs = qs.filter(cond)                           # 每个 token 都必须命中：AND 语义

为什么是 AND：brake chamber volvo 里三个词都是筛选条件，OR 会把所有刹车件都倒出来。品牌走别名表是因为客户会写 Benz、MB、奔驰，而库里统一存 Mercedes-Benz。字面全不中时（多半是拼错，如 brake chambr）才用 TrigramWordSimilarity，阈值 0.3，分数打 0.6 折——它的可信度明显低于字面命中，排序上必须靠后。

SKU 分支最简单：sku__iexact 命中就直接返回，否则按 sku__istartswith 列出，方便运营输 FIT-BPD 看整个刹车片系列。

9. 排序与去重

所有候选合到一起后，先按产品去重（保留该产品的最佳候选），再按一个四层排序键排序：

@property
def sort_key(self):
    part = self.part
    return (_PRIORITY[self.match_type],   # 1. 匹配类型：精确 < 归一化 < 前缀 < 模糊 < 名称
            -self.score,                  # 2. 同类型内分数高的在前
            -part.completeness_score,     # 3. 分数相同，资料全的在前
            part.sku)                     # 4. 兜底：稳定排序，测试可断言

第三层是业务判断而非技术选择：两个同样可信的候选，资料全的那个销售更愿意直接用（有图、有包装、有报价，能立刻回复客户）。第四层保证同样条件下顺序确定，否则测试会随数据库返回顺序抖动。

还有一个容易被忽略的 N+1：产品卡要显示"制动系统 / 制动气室"这样的分类全名，而 Category.__str__ 会读 parent.name。所以 matcher 的每一级查询都带着 select_related("part__category__parent")，测试里的假数据也刻意让分类都有上级——否则这个 N+1 在测试中根本暴露不出来。

11. 匹配能力的复用

归一化和匹配写成纯服务而不是视图里的代码，最大的回报是复用：

其中图片询价的复用最关键：视觉模型读出照片上的编号后，系统并不相信它，而是把每个编号拼成 oe:<号> 交给同一个 search()。这样图片询价的结果和文字查询同样可解释，也不存在"模型幻觉出一个不存在的编号还被当成结果"的可能——不在库里的号，匹配不出任何候选。

导入向导则只用 normalize_number()，不走 search()：导入要判断的是"这一行是不是库里已有的产品"，它有更强的依据（SKU、供应商料号），且需要一次性把整批编号建成索引，用逐行模糊匹配既慢又危险。

13. 怎么调阈值

阈值不是猜的，调法写在这里供后续维护：

  1. 在 PostgreSQL 上用真实编号量一遍分布：SELECT similarity('20443906', number_norm) ...，看"错一位""错两位""完全不同"三档各自落在哪。
  2. 阈值取"错一位"的下沿——宁可多给候选，也不要漏。漏掉的代价是销售回一句"查不到"，多给的代价只是多看一眼标签。
  3. 换数据集（比如公司真实库以 10 位编号为主）要重新量：编号越长，同样错一位的相似度越高，阈值可以相应提高。
  4. SQLite 的 difflib 阈值必须单独量，两种算法不可互换。

14. 边界与下一步

现在不做什么时候值得做
向量 / 语义检索（"适合欧曼的前轮刹车片"这类自然语言）SKU 过万、文字询盘占比高时，用 pgvector 加一路召回，与现有三级并列而不是替换
以图搜图（不依赖编号的相似外观检索）图片询价占比高、且有足够的标注图之后
把 L2 与 L3 合并成一条 SQL搜索页最坏 9 条查询里有 2 条是分级带来的；如果并发压力上来，可以合并，代价是失去"前缀"与"模糊"两种标签的区分
拼音检索（"shachepian"）国内客户占比上来之后
按客户历史加权排序询价留痕积累到有统计意义时，把"这个客户常买的规格"排前面
