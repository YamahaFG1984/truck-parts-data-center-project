1. 需求要点

业务场景是北美重卡售后件：同一种零件在不同供应商、品牌、目录里编号、名称、描述都不同；反过来，编号相似的两条记录也可能是不同品类、不同车型、不同安装位置或不同规格。需要一套可靠的产品档案，满足五件事：

#能力验收时要看到的
1导入与提取编号（原始号、品牌/供应商号）、名称、品类、关键规格与适配、供应商、报价、币种、MOQ、报价日期；每条都带原始文件与工作表/页码/行号。原件不可被覆盖。
2识别疑似同一产品分为已确认归一、疑似重复、独立产品 / 待补充三类；疑似项写明触发原因、冲突字段、缺失信息、建议人工动作。不能仅凭短编号、尺寸相同、名称相似或共同 OE 号合并。
3来源可查、报价分家每项信息能看到原始来源；同一产品不同供应商的报价分别保留。
4查询与导出按任一编号、关键词、品牌、供应商查询；在归一产品下看到各品牌号、属性、各家资料与报价；看到字段级或记录级来源；导出主数据、供应商报价、待人工确认清单。
5增量加一份新资料，能识别新增、更新、冲突与待确认。

交付物除了能跑的 Demo，还有：简短说明（数据模型、流程、匹配规则、复核机制）、一份处理结果样例与异常 / 待确认清单、后续维护说明。演示时会拿一份没见过的同类资料现场跑。

2. 现有系统为什么不能直接用

第一阶段（M01–M20）的导入器是为"把供应商资料并进产品库"设计的。拿样例资料实际跑了一遍，结果如下：

现象根因违背的要求
共享一个 OE 号的两条记录被直接合并——包括品类不同（格栅与防虫网）、左右不同的陷阱对导入判定树的规则是"编号已在库 → 更新该产品"不能仅凭共同 OE 合并
同一文件里两条共用 OE、左右不同的记录，后一条被判为"与前一行同一产品"并跳过文件内按编号去重冲突必须交人，不能吞掉
EUR、GBP 报价全部丢弃，提示"需要汇率，未导入"第一阶段约定 USD 单币种保留币种；各家报价分别保留
第二家供应商的名称、适配、尺寸只用来"补空白"，自己的写法没有留下数据直接写进产品主表，没有来源层原件不可覆盖；每条信息可回看出处
"左 / 右"列被映射为"忽略"模型里没有安装位置字段位置是区分左右件的关键规格
无 OE 但名称、适配、尺寸都相同的记录各建各的，没有任何疑似提示重复检测只有"同一 OE 挂多个 SKU"一条规则要识别疑似重复并说明原因
供应商的行号被当成我方 SKU，报价日期被忽略标准字段里没有"源记录 ID""报价日期"要保存定位信息与报价日期

结论：不在旧导入器上打补丁，而是新增两个 app，建立"来源层 → 归一层"的结构；第一阶段的产品库、搜索、询价、报价功能保持不变，作为"类似项目"附带演示。可复用的部分：项目骨架与 CI、编号归一化与品牌别名、导入向导的交互模式、列映射的同义词与大模型回退、复核台的交互模式、Excel 读写、测试基建、文档配图脚本。

4. 三层数据模型

核心思路是把"资料说了什么"和"我们认为它是什么"彻底分开：前者只增不改，后者每一次变化都来自人的决定并留痕。

4.1 apps/sources：资料与出处（只增不改）

模型关键字段说明
SourceFilesupplier、file（uuid 路径）、original_name、sha256、format（xlsx / csv / pdf）、status、mapping、stats、error原件存档。同一供应商上传哈希相同的文件，提示"已导入过 #N"并拒绝重复入库。解析失败也保留原件与失败原因。
SourceRecordsource_file、supplier、record_key、version、previous（一对一，历史不分叉）、change_type；定位：locator（如 Sheet1!R12、P3/T1/R5，同一文件内唯一）以及 sheet、row_no、page、table_no；raw（原表头 → 原文）、cells（原表头 → 单元格坐标）、fields（标准字段 → 值 / 原文 / 列 / 单元格 / 规则 / 警告）、warnings；常用字段的类型化副本：supplier_sku、name、part_type、position、make、model、year_from、year_to、dims、price、currency、moq、quote_date资料里的一行。写入后不再修改（save、delete、批量 update / delete 都会被拒绝）；供应商再发同一条记录时新建一个版本，以 previous 串成版本链。"当前版本"就是没有后继的那条，由查询得出，不设可变的 is_current 标记。
RecordNumberrecord、kind（supplier_sku / oe / source_id）、number、number_norm编号索引，复用第一阶段的 normalize_number()，供查询与召回使用。
MappingTemplatesupplier、header_signature、columns、confirmed_by人工确认过的列映射。同一供应商下次来同样表头的文件时直接套用。

4.2 apps/archive：归一档案（每次变化都来自人）

模型关键字段说明
Productcode（P-00001）、status（待核 / 已确认归一 / 已确认独立）、needs_info、missing_fields、note归一产品。每条新记录先自成一个"待核"单成员产品；合并、拆分都靠人。展示用的属性由成员记录实时汇总，成员之间有分歧时标为冲突。
Membershipproduct、supplier、record_key、current_record、status（有效 / 暂停）、joined_by、decision"某供应商的某条记录属于某产品"。挂在记录身份上而不是某个版本上，所以供应商更新报价后成员关系自动延续。
ReviewItemkind、category、record_a、record_b、triggers、agreements、conflicts、missing、suggested_action、strength、evidence_hash、rules_version、status、decided_by / at、note待确认条目：疑似同一产品、信息不足、关键字段变化、同源重复等。每条都写明为什么出现、哪里冲突、缺什么、建议怎么做。
FieldChoiceproduct、field、record、value、chosen_by、reason成员之间取值冲突时，由人选定展示值，并记下依据。
DecisionLogaction、actor、at、payload、review_item审计日志：合并、判为不同、确认独立、标记待补充、移出、选值。只增不删。

5. 处理流程

  1. 上传与留存：计算 sha256，按 uuid 路径存原件，原文件名另存；同一供应商同哈希拒绝重复入库。
  2. 解析：Excel 逐工作表定位表头，逐单元格读取值与坐标，保留单元格的数字格式；CSV 按行号定位；PDF 逐页抽表，定位写"页 / 表 / 行"。无法识别表格时，文件状态记为失败并写明原因，原件仍保留。
  3. 列映射：依次尝试该供应商的模板、同义词表、大模型建议，最后由人逐列确认；确认后保存为该供应商的模板。
  4. 标准化：见 §7，每个字段都记录原文、单元格、所用规则和警告。
  5. 预检（不写库）：与该供应商已有记录做版本对比，列出新增、未变、报价更新、关键字段变化、本次未出现，以及信息缺失清单。
  6. 入库（一个事务）：写入 SourceRecord 版本链；新记录自成"待核"产品；只有报价变化时，成员关系延续；关键字段变化时，暂停成员关系并生成复核条目。
  7. 匹配：召回候选对并逐字段比对，生成待确认条目。这一步不改动任何产品。
  8. 人工复核：人的决定写回档案并记入审计日志；同一对记录在证据没变之前不会再问第二遍。
  9. 查询与导出：档案查询、产品页（带出处）、三份 xlsx 导出。

6. 字段出处

出处精确到字段，一路追到原件的单元格：

# SourceRecord.fields 中的两项（sources 是列表：OE 号、规格等可以来自多列）
"dims": {
  "value": ["122.00", "75.00", "7.00"],
  "rule": "dims_lxwxh_cm_to_cm", "warnings": [],
  "sources": [{"column": "Package Size", "cell": "G2", "raw": "122 x 75 x 7 cm"}]
}
"price": {
  "value": "51.01", "rule": "number",
  "warnings": ["单元格格式显示 $，与币种 EUR 不一致，以币种为准"],
  "sources": [{"column": "Unit Price", "cell": "H4", "raw": "51.01"}]
}
  • 产品页上每个值都可以点开，看到它来自哪个供应商、哪个文件、哪个工作表的哪个单元格（PDF 则是哪一页、哪张表、哪一行），原文是什么，按哪条规则解析，有没有警告。
  • 原件可以随时下载比对；SourceRecord 同时保存整行原文，即使原件格式特殊也能在系统里对照。
  • 大模型只参与列映射建议，不参与字段取值：每个值都来自某个单元格，而不是模型"生成"的。

7. 字段标准化

字段规则例子缺失或异常时
品类 part_type按词表（vocabulary.json）做最长匹配；先去掉位置词"Side Grille, Left side"、"Left Side Grille" 都得到 Side Grille；"Air Filter Housing Cap" 不会被截成 Housing词表外的名称保留原文，并警告"未登记品类"
位置 position优先取位置列，其次从名称里的位置词取（Left / Right / LH / RH / Driver / Passenger）名称里没写左右、位置列写 Right，得到 Right两处不一致时以位置列为准并警告；需要区分左右的品类缺位置时，列入缺失
适配 fitment品牌走别名表（新增北美品牌），剩余部分是车型，末尾的年份区间单独拆出"Volvo VNL 2018-2023" 拆成 Volvo / VNL / 2018 / 2023；"Freightliner Cascadia P3" 拆成 Freightliner / Cascadia P3只有品牌和车型、没有年份时，标记"适配不完整"
尺寸 dims解析 L×W×H 与单位，统一换算成 cm；比较时排序后逐项比，容差可配置（默认 ±1 cm）"122 x 75 x 7 cm" 得到 [122, 75, 7]无法解析时保留原文并警告
编号OE 与互换号、供应商料号、源记录 ID 分别入编号索引；一格多号先拆开复用 split_numbers()、normalize_number()编号过短（< 5 位）不参与召回
价格 / 币种价格取单元格的数值而不是显示格式；币种取币种列单元格格式写 $、币种列写 EUR 时，按 EUR 处理并警告有价无币种时不默认 USD，列入缺失
MOQ、报价日期整数；日期接受 Excel 日期与常见文本格式—列入缺失

8. 匹配规则

匹配只做两件事：找出值得人看的记录对，以及把证据摆清楚。它不改动任何产品。

8.1 召回：哪些记录对值得比较

  1. 归一化后共享 OE 或互换号（编号至少 5 位；供应商料号不参与，短编号更不参与）；
  2. 同品类 + 同适配品牌与车型，用来覆盖没有 OE 的记录，也覆盖同一供应商内的重复；
  3. 同品类 + 同位置 + 同尺寸，只用来够到完全没有适配的记录（否则它们永远不会被召回）。

不成对的情况：品类不同或左右不同，且没有共享编号。例如同一车型下尺寸恰好相同的空滤壳和风扇罩、同一车型的左格栅和右格栅，都不会配成一对，只在各自的记录页显示一条提示，比如"同适配下有尺寸相同但品类不同的记录，已按品类区分"。一旦共享了编号，同样的差异就升级为"编号冲突"或"位置冲突"，必须交人。另一条：两边都带 OE 号、但没有任何一个相同，视为不同产品，也不成对——同名同尺寸而 OE 不同，更可能是两个不同的件。

年份：两边都没写年份时不比较（很多目录从不写）；一边写了一边没写记为缺失；区间有重叠算一致（附说明），完全不重叠算冲突。尺寸按三边排序后逐项比较，容差可配置。

8.2 比对与分类

类别条件强度建议人工动作
强证据疑似同一产品共享 OE，且品类、位置、适配、尺寸一致，没有缺失强核对后确认归一（可勾选后批量确认）
无编号佐证没有共享编号，但品类、位置、适配、尺寸一致中向供应商索取 OE 号或实物图后再确认
编号冲突共享 OE，但品类不同冲突核对目录或图片；多半是 OE 录错或一号多品。建议判为不同产品，并在该 OE 上标注"存疑"
位置冲突共享 OE，但左右不同冲突确认该 OE 是否左右通用；通常判为不同产品（左右件）
规格冲突共享 OE，品类与左右一致，但适配或尺寸不同冲突核对该编号是否跨车型、跨尺寸通用；无法确认时判为不同产品
信息不足关键字段缺失（适配、一方缺年份、尺寸、需要左右的品类缺位置），无法判断弱补充缺失字段后重新匹配
待补充（单条）记录本身缺品类、位置、适配、尺寸、价格、币种、MOQ 或报价日期提示向供应商补充；补齐前作为独立产品保留
同源重复同一供应商的两条记录关键字段一致中向供应商确认是否重复报价

硬性约束：短编号相近、尺寸相同、名称相似、共享 OE，任何单一信号都不会导致合并。按已定决策，所有合并都要人来点；上表只决定"出现在哪一类、排在哪里、建议怎么做"。

8.3 规则可调

规则分两个文件，都进版本库、可评审：apps/sources/rules/vocabulary.json 放品类词表、位置词、品牌别名、单位，通常由数据运营补充；apps/archive/rules/matching.json 放关键字段清单、尺寸容差、召回用编号的最小长度、各类别的建议动作，由负责人调整。每个待确认条目都记下生成它时的 rules_version；改完规则运行 manage.py archive_rematch，只重新生成未决条目，已决条目保持原样。

9. 人工复核与回写

动作对档案的影响
确认同一产品把两条记录所在的产品合并为一个，状态为"已确认归一"
判为不同产品各自保留；这一对之后不再召回，除非证据变化
确认独立单成员产品标为"已确认独立"
标记待补充产品标 needs_info，写明缺哪些字段，进入待确认清单
移出（拆分）把某条记录从归一产品中移出，恢复成单成员"待核"产品——合并可以撤销
选定取值成员之间有分歧的字段由人选一个展示值，并写明依据
  • 每个动作都写一条 DecisionLog（谁、何时、为什么、改了什么），只增不删。
  • 决策复用：条目的 evidence_hash 由两边的关键字段计算。重新导入或重跑规则后，证据没变就沿用原决定；证据变了就重新打开条目，并标注"证据已变化"。
  • 复核界面把两条记录左右并排摆开，冲突字段标红，缺失字段标黄，每个值旁边都能看到出处。
  • 按簇复核：互相连着的配对聚成一组（通常就是一个产品家族），一次看完；冲突条目问的是"它们是不是不同"，不参与聚簇，各自单独成组，免得把左件组和右件组连成一片。
  • 合并前的保护：两边产品之间只要有任何一对已被"判为不同"，合并就被拒绝，必须先有意识地重新审视那个决定。
  • 推出的结论：合并后，两条记录已在同一产品里的其他未决配对自动记为"确认同一"，并注明由哪个条目的决定推出。
  • 被并入的产品不删除，状态记为"已并入其他产品"并指向接收它的产品，旧编号在导出和链接里仍能追到去向；它身上的"待补充"标记并入接收方。

10. 增量导入

记录身份是"供应商 + record_key"，record_key 依次取：源记录 ID 列 → 供应商料号 → 整行内容哈希。最后一种会警告"无稳定键，无法识别更新"。

预检结果判定入库后
新增这个身份第一次出现自成"待核"产品，参与匹配
未变内容哈希相同不新建版本，只计入本次文件的入库统计
报价更新只有价格、币种、MOQ、报价日期变化新建版本；成员关系延续；产品页显示报价历史
资料更新关键字段与报价都没变，只有名称原文、供应商料号等变化新建版本；成员关系延续
关键字段变化品类、位置、适配品牌 / 车型 / 年份、尺寸、OE 有变化新建版本；所在产品还有其他成员时暂停成员关系，生成"关键字段变化"复核条目；单独成品的记录无需复核
本次未出现上一版文件里有、这次没有只提示，不删除

预检页逐行列出结果和字段级差异（旧值 → 新值），人确认后才入库。

关键字段变化的复核：条目左边是新版本、右边是旧版本，变化的字段标红。两个动作都写在 apps/archive/services/review.py（归一关系只能经它写入）： "仍是同一件"恢复成员关系，并把因此已在同一产品里的待确认配对一并关闭；"已不是同一件"把记录移出成新产品。 同一记录再次发生关键字段变化时，旧的未决条目被新条目取代。与之相关的配对条目由匹配引擎照常重算：证据变了的已决配对重新打开，标注"证据已变化"。

入库后匹配仍是全量重算（结果幂等、保留条目编号）；按当前规模不必只算变化的记录，数据量上来后再改增量。

规则重算：词表或标准化规则改动后，archive_rematch --restandardize 从留存的原件、按当时确认的列映射重新推导字段（默认只预演，加 --commit 写入）。来源记录不可修改，所以结果不同的写成新版本，变化类型"规则重算"，版本说明记下词表版本与变化字段；比较的是推导出的字段与缺失项（内容哈希只覆盖原文，词表变了哈希不变）。新版本和增量导入走同一路径；只有一处不同：重算造成的关键字段变化如果与同产品其他成员的最新版本仍一致（例如品类改名，所有成员一起变），不暂停成员关系，因证据哈希变化而重新打开的同产品配对自动关闭并记入日志；变化后与其他成员不一致的，照常暂停、进复核。

11. 查询与三份导出

查询：一个输入框，可以输任一编号（供应商料号、OE / 互换号、源记录 ID，复用编号归一化与分级匹配）、关键词（品名、品类、车型）、品牌、供应商名称。结果按归一产品聚合，并标明"命中哪条记录的哪个字段"。

产品页：汇总属性（冲突标红），成员记录表（供应商、料号、原始名称、位置、适配、尺寸、OE、价格与币种、MOQ、报价日期、出处链接），相关的待确认条目，决策历史。

记录页：整行原文（原表头、单元格坐标、原文）、每个标准字段的取值与出处、警告与缺失、版本链；并提示"相似但未配对"的记录及原因（同适配同尺寸但品类不同、同品类但左右不同、两边 OE 均不相同），只提示，不生成条目。

命令行：archive_import 文件 --supplier 名称 [--map 表头=字段] [--commit] 非交互导入，默认只预检；archive_export --out 目录 写出三份 xlsx。编号查询先按归一化编号精确匹配，没有结果且输入不少于 5 个字母或数字时才做包含匹配，避免"01"这类短码命中一片。

导出一行是列
主数据.xlsx一个归一产品产品编码、状态、品类、位置、适配、尺寸、OE 列表、成员数、各供应商料号、冲突字段、待补充字段
供应商报价.xlsx一条当前版本的来源记录产品编码、供应商、供应商料号、价格、币种、MOQ、报价日期、原始文件、工作表 / 页、行号
待人工确认清单.xlsx一个未决条目类别、强度、涉及记录（供应商 + 记录 ID + 定位）、触发原因、冲突字段（两边取值）、缺失字段、建议动作、状态

12. 自动与人工的分界

系统自动做必须由人做
原件留存与去重；解析与定位；字段标准化与警告；出处记录；版本对比；候选召回、分类、证据整理与建议动作；三份导出首次列映射确认；入库确认；所有归一、拆分、判为不同的决定；冲突字段取值；补充缺失信息；规则调整

13. 后续维护

  • 新供应商或新文件：上传后首次确认列映射，存为该供应商的模板；之后同格式文件直接预检、入库。
  • 规则调整：词表改 vocabulary.json，匹配参数改 matching.json，评审后运行 archive_rematch；已决条目不受影响，证据变化的条目自动重开。
  • 人工确认的回写：在复核台操作，决定立即生效并写入审计日志；重新导入时自动沿用。
  • 命令行：archive_import <文件> --supplier <名称>、archive_export，用于批量处理与现场演示。
