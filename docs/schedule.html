施工规则

  1. 一个里程碑一次提交。提交信息用 Conventional Commits 并带编号，如 feat(catalog): three-level matcher (M07)；提交后打标签 M07。
  2. 只做清单上的事。不提前实现后续里程碑的内容，不引入清单外依赖，不重构无关代码。发现文档遗漏时先报告再动手。
  3. 验收命令必须全部通过才允许提交。验收输出原样贴给审核者。
  4. 提交后停下，等待审核。审核提出的修改作为独立的 fix(...) 提交。
  5. 更新进度。提交后把 docs/index.html 进度表对应行改为"已提交"并填 commit 短哈希。
  6. 规范来源。字段定义以数据字典为准，模块与函数命名以架构设计为准，验收标准以PRD为准。三者冲突时以架构设计为准并报告冲突。

推荐执行模型

Opus 逻辑重、需要判断与取舍的里程碑（匹配、映射、LLM 封装、图片询价、AI 补全）。Codex / Sonnet 规格已完全给定、以模板与配置为主的机械性里程碑。作者额度充裕时全部用 Opus 亦可；反之按标注分配可省约一半成本。

里程碑明细

M01 · 项目骨架与 settings 分层

Codex2h≤ 250 行

目标

可运行的空 Django 项目，settings 按 Two Scoops 分层，工具链与接手文件就位。本里程碑使用 SQLite。

文件

  • manage.py、config/__init__.py、config/urls.py、config/wsgi.py、config/asgi.py
  • config/settings/{__init__,base,local,test,production}.py：base 含附录 B 的全部键（AUTH_USER_MODEL 与 django_q 相关项在 M02 加入）；local 开 DEBUG 与 debug-toolbar；test 固定 LLM_PROVIDER=mock；production 关 DEBUG、开安全头、whitenoise 压缩存储
  • apps/__init__.py、apps/core/：models.py 定义抽象 TimeStampedModel 与 SourcedModel（source、confidence、verified、verified_by、verified_at）；views.py 一个占位首页；urls.py
  • templates/base.html：Tailwind CDN、HTMX、Alpine，顶部导航（首页 / 搜索 / 导入 / 看板 / 审核 / 询价 / 后台），页脚"演示数据"声明；static/vendor/ 放 htmx.min.js 与 alpine.min.js 本地副本
  • requirements/{base,local,production}.txt、pyproject.toml（ruff：line-length 100，select E F I UP；pytest：DJANGO_SETTINGS_MODULE=config.settings.test，testpaths=apps）
  • .env.example（附录 B 全部键）、.gitignore、README.md（三行简介 + 指向 docs/）
  • AGENTS.md、CLAUDE.md：内容见本页交接说明，两个文件内容相同
  • apps/core/tests/test_smoke.py：首页返回 302（未登录）与登录后 200

验收

git init && python -m venv .venv && source .venv/bin/activate
pip install -r requirements/local.txt
cp .env.example .env
python manage.py check              # System check identified no issues
python manage.py migrate            # SQLite，成功
ruff check .                        # All checks passed
pytest -q                           # 2 passed
git add -A && git commit -m "chore: project skeleton with layered settings (M01)" && git tag M01

审核清单

  • config/settings/base.py 没有任何硬编码密钥或绝对路径。
  • INSTALLED_APPS 使用 apps.core 形式。
  • .gitignore 含 .env、media/、db.sqlite3。
  • AGENTS.md 与 CLAUDE.md 内容一致。

# 施工约定

本仓库按里程碑施工，每个里程碑一次提交、一次人工审核。开始任何工作前：

1. 阅读 docs/schedule.html，找到用户指定的里程碑（未指定时取 docs/index.html 进度表中第一个"未开始"）。
2. 阅读 docs/architecture.html 与 docs/data-dictionary.html 中与该里程碑相关的章节；验收标准见 docs/prd.html。
3. 只实现该里程碑列出的文件与要求。不提前做后续里程碑的内容，不引入清单外的依赖，不重构无关代码。
4. 发现文档遗漏、冲突或与已有代码不一致时，先在回复中说明并给出建议，等用户确认后再动手。
5. 完成后运行该里程碑的全部验收命令，输出原样贴给用户。任何一条失败都不得提交。
6. 通过后按 Conventional Commits 提交（信息含里程碑编号），打轻量标签 M<编号>，并更新 docs/index.html 进度表该行的状态与 commit 短哈希。
7. 停下，向用户报告：改动文件清单、验收输出、建议重点审核的地方。不要继续下一个里程碑。

技术约定：Python 3.12，Django 5.2，PostgreSQL 16（DATABASE_URL 未设时 SQLite），ruff，pytest。
settings 在 config/settings/ 分层；业务逻辑放 services 与 QuerySet，视图保持薄；
所有 AI 调用经 apps/ai/llm/factory.get_client()；AI 产出只能通过 AISuggestion.accept() 写入业务字段。
界面中文，字段英文，USD 单币种。演示数据均为合成，页脚保留声明。

审核流程：给项目作者

  1. 看增量。git show --stat M07 看改了哪些文件；git diff M06..M07 看内容。文件超出里程碑清单的要问为什么。
  2. 跑验收。把里程碑的验收命令自己再跑一遍，尤其是 pytest -q 与 ruff check .。
  3. 过清单。逐条核对该里程碑的"审核清单"，每条都能用 grep、页面点击或一条 shell 命令验证。
  4. 看测试。测试文件是否真的覆盖了清单里的情形；有没有"永远通过"的空测试。
  5. 提修改。把问题列给模型，要求以 fix(scope): ... (M07) 独立提交，不改写历史；修完再看一次 diff。
  6. 更新进度。确认 docs/index.html 该行状态已改。

每个里程碑的审核预计 15–30 分钟。若某个里程碑 diff 超过 400 行，可以要求模型拆成两次提交（例如 M14a 映射、M14b 执行）。
