1. 背景与目标

1.1 公司现状

公司是一家卡车配件出口外贸企业，产品覆盖欧系（Volvo、Scania、MAN、Mercedes-Benz、DAF、Iveco、Renault Trucks）、美系（Freightliner、Kenworth、Peterbilt、International）与中系（Sinotruk HOWO、Shacman、FAW、Dongfeng）重卡的常用易损件与结构件。销售通过 Alibaba、Shopify 独立站与官网获取询盘，采购从国内供应商处组织货源。

1.2 总经理描述的痛点

  • SKU 数量大。数千到上万个料号，同一个零件在不同品牌、不同供应商处有不同编号。
  • 数据不全。相当比例的 SKU 缺图片、缺 OE 号、缺适配车型、缺规格或缺价格，散落在供应商 Excel、PDF 目录、微信图片和销售个人的记忆里。
  • 响应慢。客户发来一个 OE 号、一张照片或一句描述，销售需要翻多份表、问采购、问产品经理，数小时甚至数天才能回复"是什么、能不能配、多少钱"。
  • 期望。建一个 AI 产品数据库，做到"从图片到功能再到价格"的快速响应。

1.3 MVP 目标

MVP 不是上线系统，而是一次向总经理的演示。它要证明三件事：

  1. 懂业务。理解 OE 号、Cross Reference、适配车型、供应商报价之间的关系，知道客户输入有多脏。
  2. 能落地。把岗位描述里的五块职责，做成一个可点击、可运行的工作流，而不是 PPT。
  3. 懂边界。AI 负责提取、映射、归类与文案；匹配永远基于公司自己的数据库；AI 产出永远带来源与置信度、先进待审核。

1.4 一句话定义

一个以标准化产品数据为核心的内部系统：把供应商的乱格式资料导入成标准字段，持续度量数据完整度，让销售用一个搜索框（文字或图片）秒级得到产品、替代件、供应商成本与建议报价，并用 AI 生成平台上架文案。

岗位描述里的五块职责，逐条对应到系统里的页面与 AI 介入点。

3. 用户与角色

销售（主要用户）

一天：早上打开邮箱与 Alibaba 后台，有 15 条询盘，其中 6 条只给了 OE 号，3 条给了照片，2 条给了竞品编号。需要：把每条询盘在一分钟内变成"产品 + 替代件 + 价格"的回复。今天的痛：翻表、问人、等答案。

采购

一天：收到三家供应商的新报价单 Excel，格式各不相同。需要：把报价单导入系统，与现有 SKU 对上号，看出哪家更便宜、交期更短。今天的痛：手工对照，历史报价找不到。

产品经理 / 数据运营（本岗位）

一天：维护分类、属性、关键词与适配关系；看哪些 SKU 缺什么；审核 AI 生成的内容。需要：一个能看到全局数据健康度、能批量处理、能追溯来源的工作台。

总经理（演示对象）

关心：响应速度、数据资产是否沉淀、AI 是否靠谱、成本多少、多久能用。不关心：技术栈细节。

4. 核心概念词典

术语英文解释示例
SKU / 料号SKU, internal part number公司自己的内部编号，系统内唯一。岗位描述中称 "FIT SKU"。FIT-BRK-00123
OE 号OE / OEM number主机厂（整车厂）原厂零件号，客户询价最常用的身份。一个 SKU 可能对应多个 OE 号（不同车厂、不同年代）。Volvo 20443906
Cross Reference / 互换号cross reference, interchange其他品牌（副厂、第三方制造商、竞争对手）对同一零件的编号。用于"客户给了别家的号，我们有没有对应件"。Knorr K001234，Renault 7420443906
供应商料号supplier part number供应商内部对该零件的编号，用于下单与对账。HB-2044
适配车型fitment / application零件能装在哪些品牌、车系、发动机、年份的车上。Volvo FH12 / D12 / 1993–2005
归一化编号normalized number去掉空格、横杠、点等非字母数字字符并转大写后的编号。所有匹配都在归一化编号上进行。A 000 420 15 20 → A0004201520
替代件alternative / substitute与目标件共享任一 OE 或 Cross 编号、或在同一互换组中的其他 SKU。同一 OE 的两个不同品牌 SKU
完整度completeness score一个 SKU 关键字段齐全程度的 0–100 评分。缺图 -15，缺 OE -20
来源 / 置信度source / confidence每条数据从哪来（人工、供应商文件、AI）以及可信程度。AI 来的数据默认未验证。source=ai, confidence=0.82

5. 用户故事与验收标准

功能编号 F0–F8。每条用户故事附 Given / When / Then 验收标准，作为施工进度表中对应里程碑的验收依据。

F0 后台管理（基线）

作为数据运营，我想要一个能增删改查所有产品数据的后台，以便在任何功能出问题时都有兜底入口。

  • Given 已登录的员工账号，When 打开后台，Then 能按 SKU、OE 号、名称搜索产品，能在产品页内联编辑编号、适配车型、图片。
  • Given 一个产品，When 查看，Then 能看到完整度分数与缺失项列表。

F1 供应商数据导入向导

作为数据运营或采购，我想要上传供应商的 Excel 或 CSV，系统自动猜出每列对应的标准字段，以便不用手工重排表格就能入库。

  • Given 一份表头为 "Part No. / OEM NO / Ref / Description / MOQ / FOB Price" 的 Excel，When 上传，Then 预览前 20 行并给出每列到标准字段的建议映射，每个建议带来源（同义词表或 AI）。
  • Given 建议映射，When 我修改其中一列并点击"预检"，Then 显示将新增、更新、跳过（重复）与无效（缺关键字段）的行数，并列出无效行原因。
  • Given 预检通过，When 点击"导入"，Then 全部行在一个事务中写入；任一行异常时整批回滚并提示；导入批次可在后台查看每一行的原始值与处理结果。
  • Given 同一个归一化 OE 号已存在于另一个 SKU，When 导入，Then 不覆盖，而是标记为"疑似重复"进入看板。

F2 数据质量看板

作为数据运营，我想要看到全库数据的健康度，以便决定先补哪一块。

  • Given 已有产品数据，When 打开看板，Then 显示 SKU 总数、完整度分布（0–40 / 40–70 / 70–90 / 90–100）、缺图 / 缺 OE / 缺分类 / 缺适配 / 缺供应商报价的数量，各数字可点击进入对应产品列表。
  • When 打开"疑似重复"，Then 列出同一归一化编号指向多个 SKU 的情况，并可一键跳转合并（MVP 阶段合并在后台手工完成）。
  • Given 导入或 AI 补全完成，When 刷新看板，Then 数字在 5 秒内更新（评分在写入时或批量重算后更新）。

F3 智能查询

作为销售，我想要在一个搜索框里输入客户给的任何编号或名称，以便秒级得到产品、替代件与价格。

  • Given 输入 20443906，When 搜索，Then 首位返回该 OE 对应的 SKU，标注匹配类型"精确"。
  • Given 输入 2044-3906、20 443 906 或 oe:20443906，When 搜索，Then 结果与上一条一致，匹配类型"归一化"。
  • Given 输入 2044390（少一位）或 20443906A，When 搜索，Then 返回相似候选并显示相似度，匹配类型"模糊"。
  • Given 输入 brake pad volvo，When 搜索，Then 按名称与适配车型返回候选。
  • Given 命中一个 SKU，When 查看结果卡片，Then 显示主图、名称、分类、规格、全部 OE / Cross 编号、适配车型、最低供应商成本、建议售价、替代件列表、完整度。
  • When 任何搜索完成，Then 自动写入一条询价记录（F7）。
  • Then 在 1 万个 SKU、5 万条编号规模下，单次搜索响应不超过 500 毫秒。

F4 图片询价

作为销售，我想要上传客户发来的零件照片，以便在不知道编号的情况下找到候选产品。

  • Given 一张带有可见编号的零件照片，When 上传，Then 系统给出零件类型、品牌线索、识别出的编号列表与一句描述，并自动用编号与类型调用智能查询，返回候选列表与置信度。
  • Given 照片上没有编号，When 上传，Then 至少返回零件类型与描述，并按类型 + 关键词给出候选。
  • Given 未配置大模型接口（mock 模式），When 上传，Then 页面仍能走通并返回示例结果，明确标注"演示模式"。
  • Then 所有候选均标注"待确认"，销售点选后才写入询价记录的匹配结果。

F5 AI 补全与审核

作为数据运营，我想要对一个或一批 SKU 让 AI 生成英文标题、描述、关键词、卖点、FAQ，并推断分类与属性，以便快速补齐数据，但不让 AI 直接改库。

  • Given 一个只有名称与 OE 号的 SKU，When 点击"AI 补全"，Then 生成一条待审核建议，包含上述字段与置信度，原字段不变。
  • Given 一条待审核建议，When 点击"采纳"，Then 对应字段写入产品，来源标记为 AI，审核人与时间留痕；When 点击"拒绝"并填写原因，Then 建议关闭，原因可被后续提示词优化使用。
  • Given 选择 50 个 SKU 批量补全，When 提交，Then 任务在后台执行，页面显示进度，不阻塞其他操作。
  • Then 每次 AI 调用记录提示词名称、模型、输入摘要、输出、token 用量、耗时与状态。

F6 供应商报价与一键报价单

作为采购与销售，我想要看到每个 SKU 的多家供应商报价并一键生成客户报价单，以便比价与快速回复。

  • Given 一个 SKU 有三家供应商报价，When 查看产品，Then 按单价升序显示供应商、供应商料号、单价、MOQ、交期、报价日期。
  • Given 一条询价与数量，When 输入目标毛利并点击"生成报价单"，Then 报价 = 最低成本 × (1 + 毛利)，USD 保留两位小数，可导出 Excel，含图片、描述、规格、包装、替代件。

F7 询价留痕

作为产品经理，我想要所有查询自动留痕，以便沉淀常见 OE、Cross、车型与客户需求。

  • Given 任意一次智能查询或图片询价，Then 自动记录原始输入、输入类型、命中结果、时间、操作人。
  • When 打开询价记录页，Then 可按时间、输入类型、是否命中筛选，并看到"最近 30 天未命中最多的输入"列表。

F8 平台上架导出

作为销售或运营，我想要勾选 SKU 导出 Alibaba 与 Shopify 的上架模板，以便直接批量上传。

  • Given 勾选 20 个 SKU，When 选择 "Alibaba" 导出，Then 生成 CSV，列顺序符合平台模板，标题、关键词、描述来自已审核字段。
  • Given 其中有 SKU 尚未审核或缺主图，When 导出，Then 这些 SKU 被排除并在结果页列出原因。

7. 非功能需求

类别要求
性能搜索 ≤ 500 ms（1 万 SKU / 5 万编号）；5 千行导入 ≤ 60 s；页面首屏 ≤ 1 s（局域网）。
可用性无大模型接口时（mock 模式）所有页面可走通；PostgreSQL 不可用时可退回 SQLite 运行（模糊匹配退化）。
可追溯所有编号、适配、文案字段带 source / confidence / verified；AI 调用全量审计；导入批次逐行留痕。
安全全站登录；上传文件校验类型与大小；密钥仅存 .env；不执行 Excel 公式。
部署单机；docker 只跑 PostgreSQL；一条命令生成演示数据。
界面中文界面，英文数据字段；桌面优先，手机可读。
成本单次 AI 补全 ≤ 4 千 token；演示全流程 API 费用 ≤ 1 美元量级（按 DeepSeek / 千问价格估算）。

8. 范围边界：做与不做

MVP 做

  • F0–F8 全部功能
  • 合成演示数据（含故意的脏数据）
  • 中文界面、USD 单币种
  • mock 模式与 SQLite 回退
  • 单元测试与 CI

明确不做（演进路线口头介绍）

  • 向量检索与 CLIP 以图搜图（先用视觉大模型 + 文本匹配）
  • 多语言站点与 i18n
  • 细粒度权限与审批流（只有登录 + staff）
  • 多币种、汇率、阶梯价
  • 与 Alibaba / Shopify 的 API 直连（先导出 CSV）
  • PDF 目录的表格自动识别（只做文本提取 + AI 抽取，作为 F1 的可选输入）

10. 演示脚本（5 分钟）

  1. 痛点复述（30 秒）。打开看板：几百个 SKU，一半缺图，三成缺 OE，还有疑似重复。这就是今天的数据。
  2. 导入（60 秒）。上传一份供应商乱格式报价单，系统猜出列映射，我改一列，预检显示新增 / 更新 / 重复，导入。看板数字变化。
  3. 查询（60 秒）。输入客户发来的 2044-3906，秒出产品、三家供应商成本、建议售价、两个替代件。再输入一个少一位的号，展示模糊候选。
  4. 图片（60 秒）。上传一张刹车片照片，识别出类型与可见编号，给出候选，点选确认，生成报价单并导出 Excel。
  5. AI 补全与上架（60 秒）。对一个缺描述的 SKU 点 AI 补全，进入审核台采纳，再导出 Alibaba CSV。强调：AI 只建议，人来定，每一步可追溯。
  6. 收尾（30 秒）。下一步路线与所需投入。
