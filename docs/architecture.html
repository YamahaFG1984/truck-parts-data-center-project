1. 设计目标与约束

约束对设计的影响
单人开发，一周出可演示版本最大化使用 Django 自带能力（Admin、ORM、模板、测试），不引入前后端分离，不引入消息队列中间件。
后续可能由不同的 AI 模型或工程师接手文档即规格；每个里程碑独立可验收；约定明确到文件名与函数名；避免"聪明"的隐式约定。
面试场景，需要向非技术人讲清架构层次少而清晰：页面 → 服务 → 数据；每个 AI 介入点都能指出"在哪一步、人怎么确认"。
国内网络环境大模型走 OpenAI 兼容接口；前端库用 CDN 且有本地回退；必须有离线 mock 模式。
数据是核心资产一切写入可追溯（source / confidence / verified）；AI 不直接写业务字段。

2. 总体架构

三个层次：

  • 表现层：Django 模板 + HTMX。搜索、映射确认、审核采纳等交互通过 HTMX 请求局部模板刷新，没有单独的前端工程。Django Admin 提供所有模型的后台 CRUD。
  • 服务层：纯 Python 模块，输入输出是明确的数据类或 QuerySet，不依赖 request。视图和后台任务都调用它们。这一层承担业务规则，是测试的重点。
  • 数据层：Django 模型、自定义 QuerySet 与 Manager。查询逻辑放在 QuerySet 上，让服务层和 Admin 都能复用。

决策点选择备选为什么这样选放弃了什么
Web 框架Django 5.2 LTSFastAPI + React；FlaskAdmin、ORM、迁移、认证、表单、测试一体，单人一周内最省。5.2 是 LTS，支持到 2028 年。API 优先的灵活性；前端独立演进。
数据库PostgreSQL 16 + pg_trgmSQLite；MySQLtrigram 相似度是编号模糊匹配的最短路径，django.contrib.postgres 直接支持；JSONField 查询更强。docker 一行起服务。零依赖的便携性。补救：DATABASE_URL 未设时回退 SQLite，模糊匹配退化为 Python 端 difflib。
前端交互模板 + HTMX + Tailwind CDN + Alpine.jsReact / Vue SPA；纯服务端渲染搜索即时刷新、映射表格编辑、审核采纳都是"改一小块"，HTMX 正合适；无构建步骤，接手者门槛最低。复杂前端状态管理。Tailwind CDN 不适合生产，但演示够用；static/vendor/ 保留本地副本以防断网。
后台任务django-q2（ORM broker）Celery + Redis；同步执行批量 AI 补全会跑几分钟，必须异步；django-q2 的 ORM broker 不需要 redis，任务表就在 PostgreSQL，部署只多一个 qcluster 进程。测试时设 sync=True 同步执行。Celery 的生态与可观测性。

结构化输出JSON mode + pydantic 校验自由文本解析；function calling三家兼容接口都支持 response_format={"type":"json_object"}；pydantic 校验失败则重试一次并降级为"低置信度"。严格 schema 约束。用 pydantic 在客户端补足。
图片匹配视觉大模型描述 + OCR 编号 → 文本匹配CLIP 向量以图搜图；训练分类模型零训练、零向量库，一周内可交付；识别出编号后复用文本匹配，结果可解释。无编号照片的相似度检索质量。列入演进路线。

PDFpdfplumber 文本提取 + AI 抽取（可选）表格识别；OCRMVP 只需把 PDF 变成文本喂给字段提取提示词，pdfplumber 足够。扫描件 OCR。不做。
配置django-environ + .envpython-decouple；直接读 os.environTwo Scoops 推荐；DATABASE_URL 一行解析。无。
测试pytest + pytest-django + factory_boyDjango TestCasefixture 更灵活，工厂让测试数据可读；CI 直接跑 pytest。无。
静态文件whitenoisenginx演示机一条 gunicorn 命令即可服务静态文件。高并发性能。不需要。
归一化编号存储Python 计算后写入普通字段Django 5 GeneratedField同一套归一化规则必须同时用于入库与查询输入，放在 Python 保证单一实现；SQLite 没有 regexp 函数，GeneratedField 会破坏回退能力。数据库级一致性保证。用 save() 与导入服务统一入口 + 测试补足。
业务逻辑位置services 模块 + 自定义 QuerySet胖模型；逻辑写在视图Two Scoops：视图保持薄；查询逻辑归 QuerySet；跨模型的编排逻辑（导入、匹配、报价）归 services，便于视图和后台任务复用与单测。无。

布局背后的规则

  • settings 拆分：base.py 放公共项，local / test / production 只写差异；通过 DJANGO_SETTINGS_MODULE 切换，默认 config.settings.local。密钥、数据库地址、模型接口一律来自环境变量，.env.example 列出全部键。
  • apps/ 命名空间：所有 app 放在 apps/ 下，INSTALLED_APPS 写 apps.catalog，避免与第三方包重名。每个 app 只做一件事，跨 app 的编排放在调用方的 services 里，禁止循环导入（importer 依赖 catalog 与 ai，反向不允许）。
  • 模板与静态文件：全局布局在根 templates/，各 app 模板放自己目录并加 app 名前缀，例如 catalog/part_detail.html。
  • requirements 分层：生产环境不装测试工具；pip install -r requirements/local.txt 是开发者的唯一安装命令。
  • 自定义 User：Two Scoops 反复强调项目一开始就用自定义 User 模型，之后再改代价极高。MVP 阶段它只是 class User(AbstractUser): pass。
  • 不在 views 里写业务：视图负责取参数、调服务、渲染模板；任何超过 10 行的逻辑进 services 或 QuerySet。

实践用在哪说明
Meta.constraints 的 UniqueConstraint / CheckConstraintPartNumber、SupplierOffer、Fitment用数据库约束而非 unique_together；带 name，violation_error_message 给出中文提示。
db_default（5.0+）status、confidence、verified、completeness_score默认值下沉到数据库，批量 SQL 写入也保持一致。
自定义 QuerySet.as_manager()Part、PartNumber、Inquiry例如 Part.objects.published()、.with_min_cost()、.missing("image")；Admin 与服务层共用。
django.contrib.postgres.search.TrigramSimilarity + GinIndex(opclasses=["gin_trgm_ops"])PartNumber.number_norm、Part.name_en索引在迁移里用 TrigramExtension() 与 GinIndex 建；SQLite 下迁移跳过（条件判断 connection.vendor）。
LoginRequiredMiddleware（5.1+）全站一行配置全站登录，登录页与健康检查用 login_not_required 装饰器豁免。
GeneratedField（5.0+）评估后未采用见第 3 节取舍：归一化必须在 Python 侧也可用，且要兼容 SQLite。
transaction.atomic() + bulk_create(update_conflicts=True)导入执行整批原子；重复编号按约束冲突处理而不是先查后写。
select_related / prefetch_related + Prefetch产品详情、搜索结果结果卡片一页最多 20 个 SKU，控制在 6 条 SQL 以内；测试里用 django_assert_max_num_queries。
模板 {% include %} 局部 + django-htmx搜索结果、映射表、审核台同一个视图按 request.htmx 返回整页或局部；不重复写模板。
表单 as_field_group（5.0+）与字段模板导入向导、报价表单统一表单渲染，减少模板重复。
ImageField + Pillow 校验 + 上传路径函数PartImage、图片询价校验 MIME 与尺寸，重命名为 uuid，避免路径注入。
管理命令而非 signals完整度重算评分在服务层显式调用（导入后、采纳后），另有 recompute_quality 全量命令。不用 signals 是为了可读与可测。
JSONField + pydantic 模型校验attributes、packaging、column_mapping、AI 输出数据库存 JSON，边界处用 pydantic 校验结构，避免"什么都能塞"。
Admin：list_select_related、autocomplete_fields、@admin.display全部 Admin大表不卡；外键选择用自动完成。

6. 数据模型

6.1 设计要点

  • 编号是独立实体，不是 Part 上的字段。一个 SKU 有多个 OE、多个 Cross、多个供应商料号，且每个编号都需要自己的来源与置信度。PartNumber.kind ∈ {OE, CROSS, SUPPLIER}，brand 指明编号属于哪家。
  • 唯一约束在 (number_norm, kind, brand) 上而非 number_norm 单独。不同品牌可能撞号（尤其纯数字短号）。跨 SKU 的同号冲突不在库级阻止，而是进入"疑似重复"看板，由人判断是真重复还是互换关系。
  • 替代件不单独建表。"共享任一 number_norm 的其他 Part"就是替代件，用 QuerySet 一次查询得到；避免维护互换组的同步问题。演进阶段若需人工维护互换组，再加 InterchangeGroup。
  • attributes 与 packaging 用 JSONField。每个分类的规格字段不同（刹车片是长宽厚，滤清器是螺纹与外径），用 Category.attribute_schema 描述该类需要哪些键、类型与单位，pydantic 在写入时校验。这比 EAV 表简单得多，且 PostgreSQL 的 JSON 查询够用。
  • AI 产出走 AISuggestion，不直接进 Part。建议表存完整 payload，采纳时由服务逐字段写回并打 source=ai。这是"AI 只建议"的落地方式。
  • AITask 与 AISuggestion 分离。AITask 是调用审计（每次请求一条），AISuggestion 是业务对象；一次批量任务产生多条建议，指向同一个 AITask 的不同 ai_task 记录。
  • ImportRow 保留原始行。导入出错时能追溯到"第 37 行原始值是什么、为什么跳过"，这是数据运营岗最常被问到的问题。
  • 公共字段：所有模型继承 core.TimeStampedModel（created_at、updated_at）；带来源的模型混入 SourcedModel（source、confidence、verified、verified_by、verified_at）。

7.2 matcher（三级匹配）

apps/catalog/services/matcher.py

@dataclass
class Candidate:
    part: Part
    match_type: Literal["exact", "normalized", "prefix", "fuzzy", "name"]
    score: float            # 1.0 / 0.95 / 0.8 / trigram 相似度 / 名称相似度
    matched_number: str | None
    matched_kind: str | None

def search(raw: str, *, limit: int = 20) -> list[Candidate]
def alternatives(part: Part) -> QuerySet[Part]      # 共享任一 number_norm 的其他 Part
def _fuzzy(norm: str) -> list[Candidate]            # PostgreSQL: TrigramSimilarity；SQLite: difflib 对候选池（同前 3 位）计算
  • 精确：输入未做归一化就命中 number 原文时记为 exact；归一化后命中记为 normalized。两者分数不同只是为了让界面能解释"你输入的格式不对，但我们认出来了"。
  • 前缀 / 包含：处理 20443906-1、A0004201520/2 这类带后缀变体。
  • 模糊：PostgreSQL 用 TrigramSimilarity(number_norm, q) 排序，阈值 0.45（编号短，阈值不能太高）；名称检索对 name_en 与 Fitment 的 make / model 做 trigram 与 icontains 组合。
  • 排序：先按 match_type 优先级，再按分数，再按完整度（数据全的排前面，销售更愿意直接用）。

8. 关键流程

8.1 导入向导

  1. 用户上传文件，选择供应商。视图创建 ImportBatch(status=uploaded)，调用 loader.read_table 生成预览（前 20 行）与表头列表。
  2. 视图调用 mapping.suggest_mapping，页面以表格展示每列的建议目标字段、来源与置信度，用户可改。提交后保存 column_mapping。
  3. 点击"预检"，loader.dry_run 返回将新增 / 更新 / 跳过 / 无效的行数与明细，页面用 HTMX 局部展示。
  4. 点击"导入"，loader.execute 在事务内写入，行数超过 500 时投递到 django-q2 后台执行，页面轮询状态。
  5. 完成后跳转结果页：统计、疑似重复列表、逐行结果链接。

8.2 图片询价

  1. 上传图片，Pillow 校验并压缩到长边 1280、JPEG 质量 85，保存到 media/inquiries/，创建 Inquiry(input_type=image)。
  2. 调用 llm.describe_image(prompt_name="image_identify")，得到 pydantic 对象 ImageFinding(part_type, brand_hints, visible_numbers, description, confidence)。
  3. 对每个 visible_numbers 调用 matcher.search；若无编号，用 part_type + brand_hints 走名称检索。合并去重后展示候选与识别结果。
  4. 用户点选候选，写入 Inquiry.matched_part，可继续生成报价单。

8.3 AI 补全与审核

  1. 产品页点击"AI 补全"，或列表多选后"批量补全"。单个同步执行，批量投递到 ai.tasks.enrich_parts(part_ids)。
  2. 服务组装上下文（名称、分类、已有编号、适配、属性、同类已审核样例 2 条），调用 extract_json(prompt_name="enrich_part", schema=EnrichResult)。
  3. 结果写入 AISuggestion(status=pending)，附 AITask。
  4. 审核台逐条展示"当前值 vs 建议值"，采纳时逐字段写回 Part 并标 source=ai，重算完整度；拒绝时记录原因。

9. 安全与数据治理

  • 三字段治理：所有可被 AI 或导入影响的实体带 source（manual / import / ai）、confidence（0–1）、verified（人工确认）。查询结果与导出按 verified 与 status 过滤。
  • AI 不直接写业务字段：只有 AISuggestion.accept() 这一条路径把 AI 内容写入 Part，代码评审时可以 grep 检查。
  • 上传校验：扩展名白名单、大小上限、Excel 用 openpyxl(data_only=True) 不执行公式、图片用 Pillow verify() 后重新编码保存、文件名改为 uuid。
  • 认证：LoginRequiredMiddleware 全站登录；Admin 仅 staff；MVP 不做细粒度权限，但成本字段在模板中以一个 can_view_cost 上下文变量控制显示，为后续权限留口。
  • 密钥：仅在 .env；.env.example 不含真实值；CI 用仓库 secrets。
  • AI 数据外泄考虑：送往大模型的内容只包含产品公开属性与供应商表头样例，不包含成本价与客户信息；提示词中明确"不要编造编号"。
